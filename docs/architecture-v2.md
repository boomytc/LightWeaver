# 事务项目与统一制作链

## 核心架构与职责边界

LightWeaver 的所有执行入口（CLI、Studio 本地 HTTP 服务以及后台作业 worker）共用同一套核心应用层 `weaver/src/app`。各产品层只通过公开的 `app` 与 `contracts` 入口交互：

- **协议真相源**：`weaver/src/contracts` 中的 Zod schema 是唯一的协议与数据结构定义。CLI 参数、HTTP 接口校验和前端状态解析共用同一套合同，避免多端各自解析产生分歧。
- **项目身份与可搬迁存储**：项目使用稳定的项目 ID 标识，不依赖创作方法、工作流名称或磁盘目录。可变状态（当前项目与库指针 `head`）和不可变版本记录存放在 SQLite 中；原始媒体、语音、渲染帧等二进制字节按 SHA-256 摘要存入内容寻址存储（CAS）。数据库内的位置引用只保存相对路径，运行根目录由 `LIGHTWEAVER_DATA_DIR`（或 CLI `--data-dir`）决定，因此整份数据库与 `blobs/` 可以一起迁移到其他位置。JSON 只用于显式导入导出和不可变快照交换，不作为并发运行时的直接读写存储。

### 为什么用 SQLite 短事务，而不是 JSON 文件锁

多进程并发操作项目时，修订乐观锁（`expectedRevision`）、请求幂等去重（`requestId`）、作业租约防脑裂（fencing）以及交付集合切换必须在同一个提交点内同时成功或一起回滚。如果只依赖 JSON 文件加锁，很难在这些跨实体状态之间保持原子一致性。

因此，LightWeaver 使用 SQLite 短事务统一承接并发控制，固定依赖 `better-sqlite3` 12.6.2，运行基线为 Node 22 / Node 24（实际兼容范围见 [package.json](../package.json) 中的 `^22.13.0 || ^24.0.0`）。

### 为什么采用两阶段编译，而不是渲染器各自计时

如果让视频渲染器、配音合成和字幕烧录各自估算时间轴，极易出现非整数帧率累计误差、声画漂移，以及无法精准复用的缓存问题。LightWeaver 将制作链路明确拆成两段：

1. **冻结输入与准备事实**：提交制作作业（`run`）时，先将当前项目修订、素材版本、库版本、模型绑定与本地工具版本全部冻结成不可变快照；随后的准备节点执行媒体探测（probe）、语音合成（TTS）与字幕强制对齐，得到确定的微秒时长、采样数和句界等客观事实。
2. **纯编译输出整数帧计划**：纯编译器消费冻结输入与准备事实，一次性计算出精确到整数帧与音频采样数的 `TimelineManifest`。所有最终画面合成、音频混音、字幕生成以及 OTIO / 剪映交接包全部严格消费同一份计划。

在这条链路中，`products/study-films/` 里的 Remotion 仅负责把文字卡片渲染成无声视频片段，不负责整片时间轴或声音混音；原始素材、画面观察证据、创作方案、候选选段与作者文案彼此独立保存，核心层不会替作者代写旁白。

## 实施结果

- **事务并发与客户端冲突保护**：SQLite 状态库、CAS 字节存储、不可变项目修订、不可变库版本和公开应用入口均已落地，CLI 与 Studio 共用同一套作业执行器（runner）。当两个 CLI 写入进程基于同一个 `expectedRevision` 并发修改同一项目时，条件更新保证恰好只有一方成功，另一方返回修订冲突；在 Studio 中发生冲突时，界面会保留用户的未提交草稿以便对照或备份恢复。
- **混合场景与共享声音计划**：制作链已跑通 `card`（文字卡片）、`still`（静帧图片）与 `clip`（视频片段）混合成片，以及横屏（`landscape`）、竖屏（`portrait`）、方形（`square`）三种输出画幅。片段的按源时长播放（`source`）、语音超窗拒绝（`reject`）、有限定格（`freeze`）与显式变速（`speed`）策略均已分别验证。正式混音与精修导出共享同一套 `AudioSegment` 定义，交接包中的独立备选音轨也会按同一计划完成裁剪、循环和变速烘焙。
- **完成收据、交付登记与崩溃恢复**：作业节点先校验产物并写入 CAS 和完成收据（同时持久化在数据库 `node_receipts` 与节点工作目录），再通过事务原子登记目标交付。因此执行整库备份与恢复后，已完成步骤的收据仍可被安全复用。对于进程异常退出遗留的运行期锁定标记（operation pin），系统会在恢复阶段检测进程存活并自动释放，防止垃圾回收（GC）被已退出的进程永久阻塞。
- **细粒度缓存与失效隔离**：缓存键与交付是否处于最新（`current`）状态同时追踪项目语义内容、模型 provider 绑定、工具版本、字体和卡片渲染指纹，各维度互不干扰——修改项目标题不会进入 TTS 计算键；不同语言（`locale`）与音色版本分别控制各自语音的缓存失效；向量检索结果按输入文本和模型绑定保存；源分析记录完整保留时间区间与对应模型绑定。

## 验收范围调整

- **真实模型功能确认**：实施初期用户曾要求跳过真实模型验收，随后明确提供了两款 VLM（DeepSeek 与 ModelBest MiniCPM-V）、ModelBest VoxCPM2 以及本地 TEN VAD 与 Qwen3-ASR 路径用于全链路确认。这些模型链路均已实际跑通，但短样例仅用于功能连通性确认，不作为最终模型选型或生产级质量结论。
- **对齐与检索模型演进**：架构升级初期尚未配置强制对齐与向量检索模型；后续已替换为 Qwen3 强制对齐、GGUF 向量检索与可选重排（早期 MLX 与 GGUF 功能验证见[专项记录](acceptance-alignment-search.md)）。自 2026-11-02 起，强制对齐固定使用 Torch 后端，现行配置与约束见[模型边界](conventions.md#模型边界)。人工 SRT 导入与纯文本检索可不依赖上述本地模型独立运行。
- **剪映与 OTIO 导出确认**：测试环境的剪映最初检测为 11.1.0，首次启动后自动升级至 11.7.0；导出 profile 因此锁定 macOS 11.7.0、草稿 schema `360000`、`adapter v1`。已实际在剪映中打开并播放包含混合场景、原生中文字幕、真实配音母带与静音备选音轨的导出草稿；OTIO 官方库（`opentimelineio` 0.18.1）重载与跨目录移动包检查已另行完成。

具体验收命令、产物摘要与未验证范围见 [docs/acceptance-v2.md](acceptance-v2.md)。
